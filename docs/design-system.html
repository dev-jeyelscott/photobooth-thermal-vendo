Canonical Admin UI Contract

Mandatory visual and interaction contract for authenticated ThermaSnap admin pages. It documents the strongest recurring repository patterns, resolves accidental differences, and defines missing reusable contracts without changing domain behavior.

Repository findings

Evidence classification from the current read-only HEAD.

Canonical

Tailwind CSS 4 semantic variables in resources/css/app.css; shadcn new-york primitives; Radix behavior; Lucide icons; resolver-owned sidebar AppLayout; p-4 lg:p-6 admin spacing; 36px default controls; semantic status tokens; accessible aria-invalid form wiring.

Normalize

Page headers vary between shared Heading and custom report headings. Summary cards vary in radius, icon size, shadows, and color strategy. Management pages repeat local status mappings, filters, tables, empty states, and pagination patterns.

Exception

Dashboard and Reports may use charts and denser metrics. Settings may use split section cards. Templates may expose drag reorder controls. These are workflow exceptions, not general page templates.

Deprecated

Hard-coded status or summary palettes such as violet, emerald, amber, sky, and red when semantic tokens exist. Page-local control clones and page-specific status color maps should not be copied into new work.

Missing

Reusable application-level PageHeader, Field, Textarea, native Select contract, StatusBadge, SearchInput, FilterToolbar, Pagination, EmptyState, and responsive data-view composition.

Primitive palette versus semantic API

Use

  • bg-success-subtle text-success
  • border-destructive for invalid controls

Interaction states

Hover

Primary uses a subtle opacity shift. Outline/ghost use accent. Rows may use muted/20. Never change meaning on hover.

Active / selected

Selected navigation uses sidebar accent or a bordered background surface. Selected statuses keep semantic text labels and do not depend on fill alone.

Focus / disabled

Focus-visible uses ring with a 3px halo. Disabled controls use opacity-50, non-interactive cursor behavior, and retain readable labels.

Canonical sizing

Controlssm 32px, default 36px, lg 40px. Input and Radix Select already use 36px default.
Icons14px compact, 16px default, 20px emphasized. Button children default to 16px.
Sidebar256px expanded, 288px mobile sheet, 48px icon rail.
Content80rem maximum where a bounded workspace is useful. Wide management tables may consume available sidebar inset width.
Dialogssm 24rem, md 32rem, lg 42rem. Choose the smallest width that avoids compression.
Density. Comfortable spacing is the default. Dense spacing is allowed for data-heavy tables and compact toolbars, never for destructive confirmations, critical forms, or touch-first flows.

Table header

Muted surface, text-left by default, medium label, 12px vertical and 16px horizontal padding.

Rows

16px horizontal/vertical comfort for management tables. Row hover is subtle muted background. Numeric values align right and use tabular numerals.

Actions

Keep one obvious edit/action when useful. Put low-frequency/destructive actions in contextual menus. Do not overload every row.

Canonical status system

Domain states map into five semantic meanings. The same meaning uses the same semantic color everywhere.

NeutralInfoSuccessWarningDanger
Domain stateSemantic stateReason
Active, Success, Completed, Printed, UsableSuccessHealthy or successfully complete.
Ready, Scheduled, Processing contextInfoInformational, ready, or scheduled without urgency.
Pending, Payment pending, For review, Needs attentionWarningRequires time, review, or operator awareness.
Disabled, Cancelled, Expired, AbandonedNeutralInactive or terminal without current failure.
Failed, Blocked, Exhausted when action is requiredDangerFailure or blocked operation requiring corrective action.
Context matters. “Expired voucher” can be neutral when merely historical, but warning when it is part of a current “needs attention” work queue. The label and surrounding workflow determine urgency. Do not encode urgency by changing colors arbitrarily per page.

Dialog / AlertDialog

Use for blocking decisions. Trap focus, Escape closes when safe, restore focus to trigger. High-impact destructive operations must state the exact resource and consequence.

Sheet / Drawer

Use for navigation and secondary mobile filters. Do not move primary form completion into a drawer without a workflow reason.

Popover / Tooltip / Dropdown

Use for transient supporting controls. Tooltip is never the sole source of essential information. Dropdown destructive items remain visibly distinct.

Search and filtering

Desktop

Compact toolbar. Search gets flexible width. Common high-signal filters remain inline. “Reset” appears only when a filter is active.

Mobile

Search remains visible when primary. Collapse secondary filters into a Sheet when the toolbar becomes crowded.

Progressive disclosure

Do not expose every possible filter by default. Add filters only when they support real operator decisions.

Documented exceptions

Dashboard

Metric-first overview and charts. It may be denser than CRUD pages.

Reports

Dedicated Daily / Monthly / Date Range sub-navigation and period/export controls.

Settings

Split section cards can pair explanatory context with grouped controls.

Templates

Drag reorder and media previews are domain-specific operational controls.

Responsive contract

Responsive behavior is defined by composition changes, not only breakpoints.

Desktop: persistent/collapsible sidebar, inline toolbar, wide tables, visible secondary actions.
Tablet: collapsed sidebar as needed, wrapped toolbar, reduced secondary information.
Mobile: drawer navigation, stacked actions, single-column forms, filter sheet, card/list data when tables become unusable.

Mobile

16px page padding. Full-width primary action when needed. Minimum touch target should approach 44x44px for touch-dominant controls even if visual control height is 36px.

Tablet

Keep data priority explicit. Hide only secondary columns that can be reconstructed from a row detail or card layout.

Desktop

24px page padding. Preserve readable line lengths. Do not stretch form fields to full viewport width when their values are short.

Accessibility contract

Target WCAG 2.2 AA behavior. Prefer native semantics before ARIA.

Keyboard and focus

All admin controls are keyboard operable. Focus-visible is always perceivable. Dialogs trap focus and restore it. Logical DOM order matches visual order.

Forms

Every control has a programmatic label. Errors are associated by ID. Required state is exposed. Invalid state uses text plus visual treatment, not color alone.

Data

Use semantic tables with caption or accessible name, header cells, and meaningful action names. Responsive cards use article, dl, headings, or equivalent semantics.

Icon-only controls

Always provide an accessible name such as “More actions for VCH-8H4K-22”. Decorative icons use aria-hidden="true".

Contrast and status

Maintain AA contrast. Status communicates meaning through text and, where useful, shape/dot/icon as reinforcement. Never rely on color alone.

Motion and zoom

Honor prefers-reduced-motion. Content must reflow under browser zoom without clipping critical controls or forcing two-dimensional scrolling.

Dark mode contract

Dark mode preserves semantic hierarchy. It is not an inverted afterthought.

Light hierarchy

Background → bordered card → elevated popover.

System settings

Muted text remains subordinate without becoming unreadable.

Dark hierarchy

Background → bordered card → elevated popover.

System settings

Borders, text, statuses, and focus remain intentional.

Surfaces

Use dark token values for background, card, popover, sidebar, and border. Avoid light-only hard-coded fills.

States

Focus, hover, disabled, selected, and invalid states must be explicitly legible in dark mode.

Status

Use semantic dark token values. Do not mirror light palette classes manually inside pages.

Content and microcopy

Use concise, plain-language operator terminology and the application’s existing domain vocabulary.

Preferred

  • New voucher
  • Save changes
  • Delete voucher
  • Try again
  • No payments found
  • Session price
  • Maintenance mode

Avoid

  • Initiate Voucher Creation
  • Execute Delete
  • Submit Modifications
  • Retry Operation
  • No Data Available
  • Unexplained abbreviations
  • Technical backend wording in customer/operator feedback

Sentence case

Page titles, buttons, labels, filters, empty states, and confirmations use sentence case unless a proper noun requires otherwise.

Dates and money

Admin-facing dates use clear locale-aware formatting. PHP currency formatting uses the actual contract value when present. Technical IDs remain monospaced and truncatable with full value accessible.

Errors

State what failed and what the operator can do next. Preserve safe technical evidence in logs, not verbose internal exceptions in UI.

Implementation rules

Layer visual decisions low in the stack and domain decisions high in the stack.

resources/css/app.css ↓ semantic design tokens resources/js/components/ui/** ↓ shadcn/Radix primitives resources/js/components/** ↓ application composites: PageHeader, StatusBadge, Field, FilterToolbar, EmptyState, Pagination resources/js/layouts/** ↓ application shell and navigation resources/js/pages/admin/** ↓ domain composition only

Extend before duplicating

If a primitive almost fits, extend it intentionally through variants or a shared composite. Do not fork another Input, Card, Dialog, Badge, or Button.

Semantic classes

Prefer token-backed classes such as bg-card, text-muted-foreground, text-success, and border-destructive.

Page composition

Pages should be mostly domain data, Inertia forms, Wayfinder actions, and composition of shared UI. Raw visual decisions inside pages should be exceptional.

Mandatory Rules for AI Agents

Any AI agent modifying ThermaSnap admin UI must follow all rules below before implementation.

  1. Read design-system.html before implementation.
  2. Inspect existing reusable components before creating new ones.
  3. Reuse semantic tokens instead of hard-coded values.
  4. Reuse existing primitives instead of duplicating component behavior.
  5. Preserve the canonical page hierarchy and resolver-owned admin shell.
  6. Preserve canonical form states, validation wiring, and accessible field anatomy.
  7. Preserve intentional responsive behavior and provide a mobile strategy for data-heavy interfaces.
  8. Preserve dark-mode parity for every changed canonical component.
  9. Preserve keyboard access, focus-visible behavior, semantic HTML, and accessible names.
  10. Preserve domain behavior, routes, submitted values, authorization, validation, state transitions, and data integrity unless the task explicitly changes them.
  11. Explain any intentional design-system exception in implementation notes or tests where appropriate.
  12. Avoid broad design-system changes while implementing a page-specific ticket unless the shared change is necessary to prevent duplication.
  13. Prefer extending an existing primitive over creating a competing primitive.
  14. Treat repository behavior as authoritative over screenshots or conceptual mockups.
  15. Never modify business logic merely to make a visual redesign easier.
Non-negotiable. A screenshot or design mockup defines visual intent, not application behavior. Existing repository contracts remain authoritative unless explicitly changed by the task.

Do Not: anti-patterns

These patterns create UI entropy and must not be copied into new admin work.

  • Do not create page-specific button variants.
  • Do not hard-code arbitrary status colors when semantic tokens exist.
  • Do not duplicate Input, Select, Textarea, Dialog, Card, Badge, or Button styling inside pages.
  • Do not recreate AppLayout or sidebar structures inside admin page components.
  • Do not use a different status color for the same semantic meaning.
  • Do not use chart palette tokens as generic status colors.
  • Do not place destructive primary actions beside normal primary actions without clear visual distinction.
  • Do not hide form labels and rely only on placeholders.
  • Do not use color as the only status indicator.
  • Do not invent arbitrary spacing or radius values when the scale supports the requirement.
  • Do not create a second Card component because a page needs different content composition.
  • Do not create a parallel component system beside shadcn/Radix.
  • Do not make desktop tables unusably overflow on mobile without an intentional strategy.
  • Do not use raw HTML injected pagination labels when normal text rendering is sufficient.
  • Do not make a reversible operation require a destructive confirmation dialog.
  • Do not change Inertia form names, values, Wayfinder routes, requests, or domain workflows for visual convenience.

Canonical contract summary

The minimum rules independent developers or AI agents should converge on.

Tokens

Use app.css semantic variables. Status uses neutral/info/success/warning/danger. Chart tokens are for charts. No raw palette semantics.

Components

Use shadcn new-york + Radix + Lucide. 36px default controls, rounded-md controls, bordered rounded-xl admin surfaces, restrained shadows.

Patterns

Resolver-owned shell → PageHeader → optional Summary → FilterToolbar → domain data → Pagination. CRUD behavior is consistent across resources.

Accessibility

WCAG 2.2 AA intent, semantic HTML, keyboard access, visible focus, labeled controls, associated errors, accessible overlays, non-color status meaning.

Responsive

16px mobile and 24px desktop page padding. Stack actions and forms on mobile. Convert unsuitable tables to responsive records or intentionally scroll only when data comparison demands it.

Dark mode

Every canonical component has intentional token-driven dark behavior for surfaces, borders, text, statuses, hover, focus, disabled, and overlays.
